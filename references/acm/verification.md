# ACM 验证与性能证据

验证深度与题目风险相匹配。简单题不必机械执行全部流程，复杂贪心、边界敏感实现和性能优化则需要更强证据。

## 1. 证据标签

始终区分以下状态：

- **用户声明 AC**：由用户报告，未在当前环境复现。
- **样例通过**：只证明给定样例的结果一致。
- **静态审查完成**：只完成代码与约束推理。
- **本地编译运行通过**：记录编译器、标准和实际输入。
- **边界测试通过**：列出测试类别，不把“通过”外推为完整正确性。
- **暴力对拍通过**：记录独立 oracle、生成范围、随机种子和轮数。
- **性能实测完成**：记录环境、编译选项、数据规模、对照和结果。

测试不能替代正确性依据。证据不足时使用准确标签，不写“已证明完全正确”或“保证 AC”。

## 2. 编译与静态检查

竞赛 C++ 默认基线为 C++17，同时尊重题目指定环境和原代码语言形态。工具可用时可采用：

```bash
g++ -std=c++17 -O2 -Wall -Wextra -Wpedantic main.cpp -o main
```

排查未定义行为时可另用：

```bash
g++ -std=c++17 -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp -o main_san
```

警告和 sanitizer 是证据来源，不等同于完整证明。执行来源不明代码时使用适当资源限制，不在未审查时赋予额外权限。

## 3. 样例与边界

先手推样例的关键状态，再运行。按题目选择边界：

- 最小/最大规模、单元素、全相等、严格递增/递减。
- 零、负数、接近类型上限、答案可能为空的输入。
- 不连通图、重边、自环、链和星形等结构边界。
- 多测首组与后续组之间的状态清理。
- 输出格式、空格、换行、精度和 64 位答案。

每组失败测试保存为可复现输入，不要只报告“有边界问题”。

## 4. WA：最小反例与暴力对拍

优先缩小到一个能暴露假设的最小反例，写出期望结果和实际结果，让学生手推关键步骤。

适合对拍时：

1. 写一个语义独立、在小规模下显然正确的暴力 oracle。
2. 生成覆盖结构边界的小数据，固定并记录随机种子。
3. 比较首个分歧，保存输入并最小化。
4. 修正后重跑原反例，再扩大随机范围。

复用同一个错误假设写出的“暴力”不构成独立证据。对拍通过后仍保留复杂度与正确性说明。

## 5. TLE：先渐近，再常数

1. 计算最坏时间和空间，包含测试组数、查询数及所有隐藏操作。
2. 检查数据范围是否给出各组规模总和。
3. 渐近复杂度不合格时，优先更换模型或数据结构。
4. 渐近合格但仍疑似超时，再定位 I/O、分配、拷贝、局部性和容器常数。

只有静态分析时写“预计/可能超时”并给出操作量推理。声称某优化更快时，使用相同编译选项和具有代表性的最大数据进行对照，报告环境与结果；交互题和缓存敏感测试采用相应合理方法。

## 6. RE/MLE 与未定义行为

检查越界、空迭代器解引用、失效迭代器、除零、非法移位、递归深度、栈上大数组和内存累计。必要时使用 sanitizer、 ulimit 或小规模复现。修复 UB 后再解释其余测试结果，避免把偶然运行成功当成正确。

## 7. 交互题与特殊 judge

交互题在每次询问后按协议 flush，并处理 judge 返回的终止状态。普通批处理题中“减少 flush 降常数”的经验不能覆盖交互协议。

SPJ、浮点误差、随机化和需要构造输出的题目，按 judge 规则验证，不强行逐字节比较非唯一答案。

## 8. 验证完成条件

结束调试或审查前，回答：

- 当前结论对应哪个证据标签？
- 首个反例或性能瓶颈是否已复现？
- 修改后是否重跑了原失败用例？
- 正确性依据和复杂度是否仍成立？
- 哪些风险仍未被当前测试覆盖？

学生下一步应是可执行的验证或修改任务，而不是笼统的“再检查一下”。
