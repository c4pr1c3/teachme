# 题目—代码对齐、调试与审查

适用于链接、截图、残缺题面、完整程序或孤立代码片段。目标是在可靠上下文中讲解，并在诊断时保留学生的修改权。

## 1. 先对齐上下文

### 1.1 收集证据

工具可用时，按任务需要读取链接、OCR 截图、检索题号/标题、核对输入输出和约束。工具不可用时，分析已有材料并列出缺口。

证据优先级：

1. 用户提供的完整题面与明确题目链接。
2. 可核对的官方题目页面或原始 PDF。
3. 截图/OCR 文本；对模糊字符和缺失约束保留不确定性。
4. 代码中的函数、样例、输入输出与算法结构。
5. 第三方题解，仅作候选线索，不能覆盖原题证据。

来源冲突时指出具体冲突字段，以可核对的原题为锚点；不能确认时保持候选状态。

### 1.2 判断代码完整度

- **完整程序**：能看到足以独立编译的入口、必要定义和主要输入输出。
- **核心片段**：只含函数、算法段、模板或局部声明。
- **无法判断**：上下文不足，说明还需要什么。

文件很长或只有截图时，不凭“看起来像完整代码”作保证。语言形态区分 C、C++ 和混合；保留可见标准、头文件、编译宏或平台线索。

### 1.3 判定题目匹配

- **已确认**：题号/链接可靠，或多个独立字段一致，包括输入输出、约束、样例等。
- **候选**：只有部分字段或算法结构相似，列出支持和反对证据。
- **未匹配**：没有足够证据，或证据相互冲突。

算法相似、变量名相似、使用同一模板都不是唯一题目的充分证据。候选或未匹配时仍可做局部静态分析，但将“该题考点”“复杂度是否符合约束”等结论限制在已知条件内。

## 2. 输出上下文对齐卡

代码审查、代码讲解或复杂调试开始时，先给简短卡片：

```text
上下文对齐
- 完整度：完整程序 / 核心片段 / 无法判断
- 语言：C / C++ / 混合；环境线索：……
- 题目：已确认 / 候选 / 未匹配（题目与链接，如有）
- 证据：……
- 缺口：……
- 验证：用户声明 AC / 样例通过 / 静态审查 / 其他实际证据
```

简单且上下文已经完全明确的请求可以压缩成一两行，不为了格式重复题面。

## 3. 先理解代码意图，再定位问题

将代码块映射到算法计划：输入与状态、核心转移或循环、答案构造、输出。讲解关键块维护的不变量和为什么正确，避免把逐行翻译当成代码理解。

审查优先级固定为：

`编译与正确性 → 渐近复杂度 → 边界/溢出/UB → 常数性能 → 风格与可迁移性`

低优先级风格意见不能淹没决定性正确性问题。

## 4. 调试路径

### CE

检查语言标准、缺失声明、类型与函数签名、平台扩展和多头文件冲突。区分编译器真实错误与静态猜测。

### WA

1. 对照代码意图和题意，找到最早破坏正确性的假设。
2. 构造尽可能小的反例，写出期望输出和代码实际行为。
3. 让学生手推关键状态并做最小修改。
4. 修改后重跑原反例、样例和必要边界。

### TLE

先计算包含测试组数的最坏渐近复杂度，再检查 `erase/insert`、字符串拼接、重复排序等隐藏操作。只有渐近复杂度可接受后，才把 I/O、分配和拷贝等常数项作为主要优化方向。

### RE/MLE

检查数组边界、空容器访问、迭代器失效、除零、递归深度、栈上大数组、移位与类型转换、总内存和多测状态。需要实际证据时按 `references/acm/verification.md` 使用 sanitizer 或资源限制。

## 5. 教练模式与完整审查

**教练模式**：只处理首个决定性错误。输出位置、证据、反例或最小修改提示，把修改动作留给学生。

**完整审查**：学生明确要求时，列出所有已确认问题，按严重度排序。每项包含：

- 行号或代码块。
- 问题及其触发条件。
- 正确性/复杂度/性能影响。
- 最小修改方向。
- 修改后需要的验证。

默认不整份重写。学生明确请求重写时，也先解释原代码意图和关键差异，保留可比较的旧结构。

## 6. 完整审查输出契约

```text
1. 上下文对齐卡
2. 总体结论：当前证据能支持到什么程度
3. 首要问题：位置 + 证据 + 影响
4. 其余问题：按严重度排序
5. 复杂度与边界：包含约束和测试组总规模
6. 风格/优化：仅在前面问题之后展开
7. 验证任务与学生下一步
```

用户声明 AC 时标记为“用户声明 AC”。若任务只是讲解，不必无依据地反驳；若发现确定反例，则给出反例并更新结论。所有实际运行结果按 `references/acm/verification.md` 标注，静态推断不能冒充实测。
